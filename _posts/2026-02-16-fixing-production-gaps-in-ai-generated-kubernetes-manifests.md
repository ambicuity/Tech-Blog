## The Outage

Recently, our team encountered an unexpected outage affecting a newly deployed analytics microservice. The service had been pushed to production just a week prior, with its Kubernetes manifests largely generated by a popular AI coding assistant. Initial tests in our staging environment were green, and the service performed adequately under synthetic load. The incident, however, highlighted a critical difference between "functional" and "production-grade" Kubernetes configurations, especially when relying on AI for initial scaffolding.

The outage manifested as a partial service degradation – requests to the analytics service intermittently failed, and some dependent services reported upstream connection errors. A quick `kubectl get pods -n analytics-system` revealed several pods stuck in `ContainerCreating` or cycling through `CrashLoopBackOff` on specific nodes.

The repeated `OOMKilled` events and `Evicted` warnings, despite seemingly adequate `Limits` and `Requests`, pointed to a subtle misconfiguration. Further investigation revealed that these specific nodes were undergoing maintenance, requiring pods to be drained and rescheduled. The AI-generated `Deployment` manifest had not included `livenessProbe` or `readinessProbe` definitions, nor a `PodDisruptionBudget`.

Without proper `readinessProbe`s, the service registered as `Ready` as soon as the container started, potentially before the application within was fully initialized or able to handle connections. This led to traffic being routed to unready pods during rescheduling, causing connection failures. The `OOMKilled` was a symptom: without a `livenessProbe`, Kubernetes wouldn't restart the application if it entered a hung state (even if not strictly OOM), or if it failed to initialize correctly, causing it to consume memory until eviction. While the `Limits` were present, the application's actual startup memory spike was higher, exacerbated by repeated restarts and a lack of proper health checks to signal a truly stable state. The missing `PodDisruptionBudget` meant that during node drains, multiple pods could be voluntarily evicted simultaneously, overwhelming the remaining capacity and leading to cascading failures.

This is a perfectly valid, minimalist manifest. It *works*, but it's not resilient or secure for production.

## Production Hardening

To address these critical production gaps, we augmented the manifest with several key components:

1.  **Liveness and Readiness Probes**: Essential for Kubernetes to understand the application's health and readiness to receive traffic. A `livenessProbe` restarts the container if it's unhealthy; a `readinessProbe` removes it from service endpoints until it's truly ready.

2.  **Adjusted Resource Requests/Limits**: Based on profiling the application's actual startup and steady-state memory footprint, we increased the `requests` to ensure adequate guaranteed resources, and `limits` to prevent runaway consumption while allowing for initial spikes.

3.  **Pod Security Context**: While not directly causing the outage, this is a critical security hardening. We enforced running as a non-root user, disallowing privilege escalation, and using a defined `seccompProfile`.

4.  **Pod Disruption Budget (PDB)**: To maintain high availability during voluntary disruptions (like node maintenance), a PDB ensures a minimum number of healthy pods are always running.

Here is the revised, production-hardened `analytics-service.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: analytics-service
  labels:
    app: analytics-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: analytics-service
  template:
    metadata:
      labels:
        app: analytics-service
    spec:
      securityContext: # Pod-level security context
        runAsNonRoot: true
        runAsUser: 10001 # Example non-root user ID
        fsGroup: 10001   # Example fsGroup
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: analytics-service
        image: my-repo/analytics-service:1.0.0
        ports:
        - containerPort: 8080
        resources:
          limits:
            cpu: "1000m" # Increased CPU limit based on profiling
            memory: "512Mi" # Increased memory limit based on profiling
          requests:
            cpu: "250m"  # Increased CPU request for guaranteed performance
            memory: "256Mi" # Increased memory request for guaranteed allocation
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15 # Give application time to start
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5  # Can be shorter than liveness if app quickly signals readiness
          periodSeconds: 5
          timeoutSeconds: 3
          failureThreshold: 2
        securityContext: # Container-level security context
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop: ["ALL"] # Drop all default capabilities for stronger security
```

And the associated `PodDisruptionBudget.yaml`:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: analytics-service-pdb
spec:
  minAvailable: 2 # Ensure at least 2 pods are available during voluntary disruptions
  selector:
    matchLabels:
      app: analytics-service
```

These changes immediately stabilized the service. The `readinessProbe` prevented unready pods from receiving traffic, and the `livenessProbe` ensured containers that became unresponsive were restarted. The `PodDisruptionBudget` prevented aggressive node drains from taking out too many pods simultaneously, allowing for graceful rescheduling. The adjusted resources provided a more accurate allocation for the application's lifecycle, addressing the `OOMKilled` incidents during startup spikes.

The larger takeaway is that while AI excels at generating functional code and basic configurations, it often lacks the inherent operational context that seasoned engineers build over years. AI-generated configurations tend to be "lowest common denominator" – valid, but not robust for demanding production environments. Their output reflects patterns, not necessarily deep operational understanding of system resilience, security, or specific application behaviors under stress.

## Prevention Strategy

To prevent similar issues, we are implementing a multi-pronged approach:

*   **Policy-as-Code Enforcement**: Integrating tools like OPA Gatekeeper or Kyverno into our CI/CD pipelines. These tools enforce organizational standards for Kubernetes manifests, automatically rejecting deployments that lack required probes, security contexts, or appropriate resource declarations. This provides an automated guardrail against common configuration omissions.
*   **Enhanced CI/CD Linting**: Adding more aggressive linting (e.g., `kube-lint`, `yamllint`) with custom rules to validate Kubernetes manifests for production best practices early in the development cycle.
*   **Developer Training**: Educating development teams on the nuances of production-grade Kubernetes manifests and the specific operational requirements beyond basic functionality. This includes fostering a critical review mindset when integrating AI-generated outputs.
*   **Standardized Base Templates/Helm Charts**: Providing developers with vetted, production-ready Helm chart templates or Kustomize bases that pre-include all necessary probes, security contexts, resource guidelines, and PDBs. This reduces the cognitive load and ensures a consistent baseline across all new services.

AI is a powerful productivity multiplier, but it's a tool that requires human oversight, especially in critical infrastructure domains like Kubernetes. Its output serves as an excellent starting point, but the journey to production-readiness still demands a deep understanding of system reliability, security, and operational best practices.

### Operational Checklist

- Audit all AI-generated Kubernetes manifests against organizational standards before deployment.
- Validate that `readinessProbe`, `livenessProbe`, and `startupProbe` are present and properly configured.
- Ensure `securityContext` is set with `runAsNonRoot`, `readOnlyRootFilesystem`, and `allowPrivilegeEscalation: false`.
- Review resource `requests` and `limits` for accuracy based on actual profiling data.
- Configure `PodDisruptionBudget` for high-availability deployments.
- Implement OPA Gatekeeper or Kyverno policies to enforce standards automatically.
