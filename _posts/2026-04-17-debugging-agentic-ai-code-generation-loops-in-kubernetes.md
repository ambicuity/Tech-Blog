We started experimenting with agentic AI for automating code generation and deployment of simple Python microservices on our Kubernetes cluster. The goal was to rapidly iterate on internal tools and APIs, freeing up senior engineers from boilerplate tasks. The agent was tasked with taking a high-level specification (e.g., "Create a service that returns the current system time in UTC") and generating the Python code, Dockerfile, Kubernetes manifest, and deployment pipeline.

Initially, things seemed promising. The agent generated functional code and deployed it successfully. However, we quickly encountered a critical issue: the agent sometimes entered an infinite loop of code generation and deployment, triggered by its own feedback loop.

Here's how the loop manifested:

1.  The agent generates Python code for a microservice.
2.  The agent creates a Dockerfile and builds a container image.
3.  The agent generates a Kubernetes deployment manifest.
4.  The agent deploys the microservice to the cluster.
5.  The agent runs integration tests against the deployed service.
6.  The integration tests fail due to a minor issue (e.g., incorrect timezone handling).
7.  The agent analyzes the test results and *decides* to regenerate the code based on the perceived error.
8.  The agent repeats steps 1-7 indefinitely, creating a flood of deployments and filling up our image registry.

The logs from the agent's orchestration component (written in Go) showed the following pattern:


The Kubernetes deployment manifest generated by the agent looked like this (snippet):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: time-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: time-service
  template:
    metadata:
      labels:
        app: time-service
    spec:
      containers:
      - name: time-service
        image: my-registry/time-service:latest # This was constantly being updated
        ports:
        - containerPort: 8080
```

The core problem was that the agent's logic for determining when to regenerate code was too aggressive and didn't account for transient issues or minor discrepancies.  It also wasn't idempotent; it didn't *learn* from its mistakes. Each regeneration cycle produced subtly different (but still incorrect) code.

To fix this, we implemented the following changes:

1.  **Rate Limiting:** We introduced rate limiting on the code regeneration trigger.  The agent could only regenerate code for a given service a maximum of 3 times per hour. This prevented the runaway deployments.

    ```go
    // Example Rate Limiter (using a simplified in-memory implementation)
    type RateLimiter struct {
        mu sync.Mutex
        counts map[string]int
        limit int
        duration time.Duration
    }

    func (rl *RateLimiter) Allow(key string) bool {
        rl.mu.Lock()
        defer rl.mu.Unlock()

        if rl.counts == nil {
            rl.counts = make(map[string]int)
        }

        if rl.counts[key] >= rl.limit {
            return false
        }

        rl.counts[key]++
        time.AfterFunc(rl.duration, func() {
            rl.mu.Lock()
            defer rl.mu.Unlock()
            rl.counts[key]--
        })

        return true
    }
    ```

2.  **Test Failure Thresholds:** Instead of immediately regenerating code on any test failure, we introduced a threshold. The agent now only regenerates code if a certain percentage (e.g., 50%) of tests fail consistently across multiple deployments. This helps filter out transient network issues or intermittent errors.  We added labels to the tests so the AI could better assess failure modes.

3.  **Improved Error Analysis:** We refined the agent's error analysis logic to be more specific. Instead of just detecting a "timezone mismatch," it now identifies the exact file and line number where the mismatch occurs, allowing it to make more targeted code changes. This required augmenting the integration tests with more detailed reporting.

4.  **Code Versioning and Rollback:** We implemented a system to track different versions of the generated code and the associated deployments. If a new deployment caused a regression, we could easily roll back to a previous, known-good version.  This also helped the agent "learn" which changes were effective and which weren't. We stored code versions in a Git repository tagged with deployment timestamps.

    ```bash
    # Example rollback script
    SERVICE_NAME="time-service"
    PREVIOUS_TAG=$(kubectl get deployment $SERVICE_NAME -o jsonpath='{.metadata.annotations.previous_tag}')

    if [ -z "$PREVIOUS_TAG" ]; then
      echo "No previous tag found. Aborting rollback."
      exit 1
    fi

    git checkout $PREVIOUS_TAG
    # Rebuild and redeploy from the checked out code
    # Update the k8s deployment with the new image tag.
    ```

5. **Explicit Timezone Configuration:** The root cause of the timezone issue was the lack of explicit timezone configuration in the generated Python code.  We modified the agent's code generation templates to always include `timezone = pytz.utc` where relevant.

    ```python
    # Example Python code snippet (before)
    import datetime
    now = datetime.datetime.now()
    print(now)

    # Example Python code snippet (after)
    import datetime
    import pytz
    now = datetime.datetime.now(pytz.utc)
    print(now)
    ```

By implementing these changes, we significantly reduced the incidence of infinite code generation loops and improved the overall stability of our agentic AI-powered deployment pipeline.  We learned that robust error handling, rate limiting, and version control are crucial when working with AI-driven automation in production environments.  Specifically, without clear and precise error context, the AI was simply thrashing, making random changes in an attempt to resolve the problem.
