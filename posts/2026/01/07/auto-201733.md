## Introduction
Kubernetes Secrets are the standard way to manage sensitive information like passwords, API keys, and certificates within your cluster. However, storing Secrets in plain text within YAML files, even if committed to a private Git repository, poses a significant security risk. Sealed Secrets provide a safer and more convenient solution by encrypting your Secrets so that they can be stored safely, even in public repositories, and only decrypted by the Sealed Secrets controller running in your Kubernetes cluster. This blog post will guide you through the process of setting up and using Sealed Secrets to manage your sensitive information more securely.

## Core Concepts

Let's break down the core components and concepts behind Sealed Secrets:

*   **Kubernetes Secrets:** These are Kubernetes objects used to store sensitive data like passwords, OAuth tokens, and SSH keys. While Kubernetes Secrets provide a mechanism for securely storing and retrieving sensitive data within the cluster, they are stored unencrypted by default in etcd.

*   **Encryption:** Sealed Secrets leverage asymmetric encryption. This means there are two keys: a public key used for encryption and a private key used for decryption. Only the private key can decrypt data encrypted with the public key.

*   **Sealed Secrets Controller:** This is a Kubernetes controller that runs within your cluster. It holds the private key used for decrypting Sealed Secrets. When a Sealed Secret is created, the controller automatically decrypts the encrypted data and creates a corresponding Kubernetes Secret.

*   **`kubeseal` CLI:** This is a command-line tool that allows you to encrypt Kubernetes Secrets using the public key of the Sealed Secrets controller. It's typically installed on your local machine or within your CI/CD pipelines. The output of `kubeseal` is a `SealedSecret` custom resource definition (CRD).

*   **`SealedSecret` CRD:**  This is a custom resource definition provided by the Sealed Secrets controller. It defines the structure of a Sealed Secret, which includes the encrypted data and metadata.

The core idea is that you use `kubeseal` with the controller's public key to encrypt the Secret *before* committing it to your repository. Then, the Sealed Secrets controller inside the cluster, which holds the private key, will decrypt the `SealedSecret` CRD and create a regular Kubernetes `Secret`.

## Practical Implementation

Here's a step-by-step guide to implementing Sealed Secrets in your Kubernetes cluster:

**1. Install the Sealed Secrets Controller:**

First, install the Sealed Secrets controller into your Kubernetes cluster. We will use Helm, a popular package manager for Kubernetes.

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm install sealed-secrets bitnami/sealed-secrets --namespace kube-system
```

This command adds the Bitnami repository, updates your Helm repositories, and installs the Sealed Secrets controller into the `kube-system` namespace.

**2. Verify the Controller Installation:**

After installation, verify that the Sealed Secrets controller is running correctly:

```bash
kubectl get pods -n kube-system | grep sealed-secrets
```

You should see a pod with a name similar to `sealed-secrets-controller-*` in the running state.

**3. Install `kubeseal` CLI:**

Next, install the `kubeseal` command-line tool on your local machine. You can download the appropriate binary from the Sealed Secrets GitHub releases page: [https://github.com/bitnami-labs/sealed-secrets/releases](https://github.com/bitnami-labs/sealed-secrets/releases). Make sure to download the binary that matches your operating system (Linux, macOS, or Windows).

Alternatively, you can often use a package manager:

*   **macOS (Homebrew):** `brew install kubeseal`
*   **Linux (apt):**  (Usually requires adding a repository; check the official documentation.)

**4. Create a Kubernetes Secret:**

Now, let's create a Kubernetes Secret that we want to encrypt. For example, let's create a secret named `my-secret` with a key `password` and a value `mysecretpassword`:

```yaml
# secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-secret
type: Opaque
data:
  password: $(echo -n "mysecretpassword" | base64)
```

**Important:** Note that the value of `password` is base64 encoded. Kubernetes Secrets require data to be base64 encoded.  On MacOS, use `base64 -w 0` to avoid line wrapping.

Apply this Secret to your Kubernetes cluster:

```bash
kubectl apply -f secret.yaml
```

**5. Seal the Secret with `kubeseal`:**

Now, use `kubeseal` to encrypt the Secret.  Crucially, you need to specify the namespace the *original* Secret lives in. If you don't specify a namespace, it will default to the `default` namespace, and decryption will fail if the controller doesn't have access to that namespace.

```bash
kubectl get secret my-secret -o yaml | kubeseal --format yaml --namespace kube-system > sealed-secret.yaml
```

This command retrieves the `my-secret` Secret, pipes it to `kubeseal`, encrypts it using the Sealed Secrets controller's public key, and saves the resulting `SealedSecret` definition to `sealed-secret.yaml`.  We're explicitly specifying the namespace to be `kube-system` because that's where the controller is installed.  `--format yaml` ensures the output is in YAML format.

**6. Examine the `SealedSecret`:**

Inspect the `sealed-secret.yaml` file. You'll notice that the `data` section now contains encrypted data. You can safely commit this file to your Git repository.

```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  creationTimestamp: null
  name: my-secret
  namespace: kube-system
spec:
  encryptedData:
    password: AgCrV3R... # (Encrypted password)
  template:
    metadata:
      creationTimestamp: null
      name: my-secret
      namespace: kube-system
    type: Opaque
```

**7. Apply the `SealedSecret`:**

Apply the `SealedSecret` to your Kubernetes cluster:

```bash
kubectl apply -f sealed-secret.yaml
```

**8. Verify the Secret Creation:**

The Sealed Secrets controller will detect the `SealedSecret`, decrypt the data, and create a corresponding Kubernetes Secret with the same name in the same namespace. You can verify this by checking for the `my-secret` Secret:

```bash
kubectl get secrets my-secret -n kube-system
```

You should see the `my-secret` Secret listed.  The data is now safely available for your applications to use.

## Common Mistakes

*   **Forgetting the Namespace:** Failing to specify the namespace when using `kubeseal` is a common mistake.  The SealedSecret *must* be created in the same namespace as the original secret and where the controller expects it to be.

*   **Incorrect `kubeseal` Version:** Using an outdated or incompatible version of `kubeseal` can lead to encryption errors.  Make sure your `kubeseal` version matches the Sealed Secrets controller version.

*   **Incorrect Key Scope:** Sealed Secrets supports different key scopes (cluster-wide and namespace-wide). Using the wrong scope during encryption can prevent the controller from decrypting the Secret.  The default is namespace-wide, meaning the secret can only be decrypted in the namespace it was encrypted for.

*   **Not Deleting the Original Secret:** After sealing the secret, remember to delete the original, unencrypted Kubernetes Secret.  Leaving it in place defeats the purpose of using Sealed Secrets.

*   **Losing the Private Key:**  If you lose the private key used by the Sealed Secrets controller, you won't be able to decrypt existing Sealed Secrets. Back up the key securely.  While key rotation is possible, it's a complex process.

## Real-World Use Cases

Sealed Secrets are applicable in various real-world scenarios:

*   **Storing API Keys:** Safely store API keys for third-party services within your Kubernetes cluster.

*   **Managing Database Credentials:** Securely manage database usernames, passwords, and connection strings.

*   **Storing TLS Certificates:** Encrypt TLS certificates used for secure communication between services.

*   **CI/CD Pipelines:** Integrate Sealed Secrets into your CI/CD pipelines to securely deploy applications with sensitive information. This allows you to check your application configuration into source control without exposing sensitive data.

*   **Multi-Tenant Environments:** In multi-tenant environments, Sealed Secrets can help isolate secrets between different tenants.

## Conclusion

Sealed Secrets offer a practical and effective solution for managing sensitive information in Kubernetes. By leveraging asymmetric encryption, they allow you to safely store secrets in Git repositories and deploy them to your cluster without exposing them to unauthorized access. While the initial setup requires some effort, the added security and convenience make Sealed Secrets a valuable tool for any organization deploying applications on Kubernetes. By understanding the core concepts, following the implementation steps, and avoiding common mistakes, you can effectively manage secrets in your Kubernetes environment and enhance the security of your applications.
